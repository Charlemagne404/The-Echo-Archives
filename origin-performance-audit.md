# Origin performance audit

## Current production topology and protection

Read-only inspection found the active release at `/srv/echo-archives/current` pointing to `cb6af6ae6c7a28fe5bfd272992588cda9cb5274a`. Requests flow Cloudflare → Caddy → Node on `127.0.0.1:3010` → SQLite at `/var/lib/echo-archives/community.sqlite`. Caddy's Echo site block checks that the remote peer is in Cloudflare's published IP ranges. UFW is active; the public interface is `188.149.200.166`, with ports 22, 80 and 443 allowed. Thus TCP 80/443 is directly reachable at the host firewall, while the Echo vhost has a Caddy peer allowlist. A direct-origin HTTP request was not sent during this read-only task, so response behavior is inferred from configuration, not externally probed. No firewall changes were made. Staging uses a separate release/database and loopback port 3011.

Caddy had no Echo access log configured. This prevented request-to-upstream and response-status attribution. No reverse-proxy error log or app request log covering the relevant burst was available in the inspected sources. Do not infer that the 504s were generated by Node from the Cloudflare 504 label alone.

The directly countable dynamic/miss viewer requests total **17,000**. A previous 27,346 approximation added blank-status requests and UPDATING viewer responses. Those categories cannot be treated as actual origin fetches: blank status is unknown, while UPDATING can represent one background update shared by multiple viewers. Actual background updates, revalidations, expired objects, and cache locks require Cloudflare request/origin logs to quantify.

The supplied 42,182 weekly HTTP 504 responses, including 5,646 during the November 11 incident, are not attributable to Cloudflare, Caddy, Node, the database, or a downstream service with current evidence. The observed November 8 Caddy journal contains 273 `502` upstream connection-refused errors to `127.0.0.1:3010`; these establish a separate app-not-listening interval, not the source of the November 11 504s.

## App and database work traced

- Public catalogue routes are rendered from loaded catalogue state. Each request currently checks the revision of six public data files; the mitigation limits these stats to once per second per Node process.
- Public show pages obtain review/score data through four synchronous SQLite reads (review count/page and rating/score summaries). This is bounded but repeated for every uncached show request. No production query-latency histogram or connection-saturation evidence is present.
- Generated cover/social image and versioned assets are static files. They should be served from cache after a correct initial fill.
- Search/filter pages vary by query and must not be shared-cache entries. Public, queryless show/creator/collection HTML is stable for anonymous visitors.
- App process snapshot observed earlier was approximately 254 MB current RSS and 697 MB peak with no recorded cgroup memory events or CPU throttling. These are a single snapshot, not burst-time history.
- Production HTML previously used `Cache-Control: no-cache`. `/data/shows.json` was 10,264,707 bytes with `max-age=0,must-revalidate,SWR60`; `must-revalidate` defeats stale serving. Popularity scores used a 60-second cache.

The data supports useful cache offload but does **not** prove that SQLite or a single route caused the 504s. Add bounded request/route timing and Caddy status/upstream timing logs before claiming a root cause. Keep query timeouts and concurrency limits evidence-driven; do not enlarge timeouts to conceal saturation.

## Implemented origin changes

The isolated code adds shared-cache headers only where route identity is stable; it keeps browser revalidation for HTML/JSON and gives CDN edges bounded freshness plus stale-while-revalidate/stale-if-error. Exact versioned asset query hashes receive one-year immutable caching. Generated images get one-day CDN freshness with seven-day stale windows. Six public-file stats are rate-limited to once/second per process.

An in-process cache proxy regression fixture checks same-resource reuse and independent query keys. A 240-show traversal made 240 first-pass origin requests and zero second-pass requests through that proxy; the benchmark is local synthetic evidence, not a Cloudflare cache-hit forecast. The cached traversal still visits all distinct shows once per edge cache location/expiry.

Candidate UFW procedure, **not applied**:

1. From an out-of-band console, capture `sudo ufw status numbered` and `sudo ufw status verbose`; identify the exact all-source 80/443 allow entries and all monitoring sources. Do not remove SSH or monitoring rules.
2. Install allow rules for every current IPv4 and IPv6 CIDR above on TCP 80 and 443. If IPv6 is disabled in UFW, first establish whether the host has a public IPv6 listener and whether Cloudflare reaches it. Keep the existing TCP 22 rule in place.
3. Verify the CIDR allow rules are active, then remove only the previously identified all-source TCP 80/443 allows by exact rule ID (remove IDs in descending order because UFW renumbers). The default incoming policy must remain deny. Do not remove a global rule until all Cloudflare allow rules are confirmed.
4. Verify `ufw status numbered`; test `https://echoarchives.net/api/health` through Cloudflare and direct origin IP with the correct Host/SNI from an authorized external probe. Confirm monitoring remains green and SSH remains reachable from the operator's current session.
5. Keep an out-of-band console and timed operator rollback ready. If proxied health, monitoring or SSH fails, restore the saved firewall rules from that console. Store the allowlist as managed data and review it on Cloudflare range updates.

This candidate is intentionally a human-applied sequence, not a runnable shell script: current rule IDs, IPv6 state, monitoring sources, and out-of-band access must be verified before removing existing broad allows. Cloudflare's [origin configuration guidance](https://developers.cloudflare.com/fundamentals/concepts/cloudflare-ip-addresses/) recommends allowing its ranges and blocking other origin traffic.
